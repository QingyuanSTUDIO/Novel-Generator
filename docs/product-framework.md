# 小说生成器：产品与技术框架 v0.1

日期：2026-09-30。状态：设计提案，待真实开发验证；当前没有已实现的应用功能。

## 1. 产品定位与首版边界

以章节为中心的长篇小说创作工作台：作者维护设定与计划，AI 按明确上下文生成候选正文，作者审阅后形成定稿，再更新故事状态。

默认面向单人、本地运行、联网调用模型的使用方式。一个桌面应用管理多部作品，作品的数据严格隔离。桌面界面使用 Vue 3，后端服务在本机运行。首版不引入账号体系、多人协作、云同步、向量数据库、自动连续写完整本书。

核心创作模块全部进入首版：世界书、文风规则、角色卡、道具卡、大纲、世界引擎。API 连接和模型配置是全局基础设施；每部作品可以选择默认 API 和独立文风。

成功标准：能创建作品、维护六类资料、连接真实 API、生成一章、审阅并采纳、确认状态变化，再生成下一章；关闭重开后内容与任务记录仍在。

## 2. 信息架构与页面布局

### 2.1 两级导航

- 全局：作品书架、API 配置、应用设置。
- 作品内：写作、世界书、角色、道具、大纲、世界引擎、文风。

顶部显示当前作品、当前章节、保存状态与任务入口。章节写作时只展示当前预设的快捷选择，复杂密钥与模型参数集中到全局设置。

### 2.2 写作工作台

桌面宽屏结构：左侧作品导航（约 80–120px）＋章节目录（约 220px）＋中央正文（弹性，建议最小 480px）＋右侧助手（约 320px）。目录和助手均可收起、调整宽度，提供专注写作。

- 左侧目录：卷 → 章，展示草稿、待审阅、已定稿标识；切换章节保留编辑状态。
- 正文顶部：章名、版本、字数、保存状态；编辑器工具栏保持克制。
- 正文底部或选中文字菜单：续写、改写、扩写、润色。整章生成从右侧章节任务发起。
- 右侧三个标签：本章任务、本次资料、检查建议。默认显示章节目标、出场角色、关键道具、世界引擎动作和生成按钮。
- 本次资料：列出实际注入条目、命中原因、采用版本、预计输入量；可手动纳入或排除可选资料。硬约束不能静默取消。
- 生成候选进入独立草稿版本；查看原文与候选差异，按段或整章采纳，保留撤销与旧版本。

适配：宽度 ≥1440px 可展开全部区域；1024–1439px 默认收起章节目录，通过按钮打开；768–1023px 采用正文＋单个侧栏；更窄时单列切换。正文中文建议 17–18px、行距约 1.8，可调字体与宽度。实际断点通过实现阶段的布局测试校准。

### 2.3 资料页面

世界书、角色、道具使用「条目 / 卡片选择＋详情编辑」布局。卡片封面只显示名称、类型、当前状态、简述；复杂字段和历史放在详情页，避免把所有字段铺满首页。世界书详情额外显示触发条件、注入位置、优先级和本章命中预览。不要用人物关系图替代可编辑列表，关系图放后续迭代。

大纲采用「全书 → 卷 → 章 → 场景」树与详情面板。世界引擎统一管理时间、角色行动、事件、线索和待确认提案。文风页采用「规则组＋启用状态＋正反例」布局。

视觉建议：低饱和中性色、一个强调色、清晰留白；正文占视觉中心，图标辅以文字；明暗主题兼容；保存中、保存失败、生成中、未配置模型均有明确状态。

## 3. 六个核心模块的规范

### 3.1 世界书：管理稳定设定

这一模块参考 SillyTavern World Info 的“动态词典”思路：世界书不是一篇每次都塞进上下文的百科，而是一组可独立触发、可解释、可排序、可限额注入的条目。分类：世界规则、地理地点、组织势力、历史、能力体系、社会习俗。角色与道具用专用卡片维护，世界书通过 ID 引用，避免同一事实重复存储。

每条包含：名称、分类、别名、简述、正文、标签、关联实体、启用状态、版本。另含：

- 约束强度：硬设定 / 背景参考。
- 触发方式：常驻、章节 / 卡片关联、关键词、正则表达式、手动；首版默认关闭不可解释的语义向量触发。
- 触发键：主关键词、可选的 AND / NOT 过滤词、大小写与整词匹配选项。中文默认按短语匹配，不依赖空格分词。
- 注入位置：上下文资料区、写作约束区、章节开头提示、任务末尾提醒。小说正文不使用聊天消息深度作为默认概念，但保留“相对顺序”和“相对章节阶段”。
- 优先级与预算：数值顺序、条目预算；常驻硬设定先入，直接命中的条目优先于递归命中的条目。超预算时显示被裁剪条目及原因。
- 递归策略：条目内容可以激活其他条目，但限制最大递归层数并记录触发链；提供不可递归、禁止继续递归、仅递归触发三个选项。
- 互斥组：同一场景下有多个替代背景时，可设置确定性的互斥组并由优先级或作者选择保留一个；核心路径不使用随机概率，避免同一章节无法复现。
- 适用范围：全书、卷、章或故事阶段。
- 有效时间：从哪个故事状态开始生效、何时失效。
- 保密信息：作者真相、读者揭露节点、可获知角色；这些是创作信息边界，不是账号权限。

首版只允许少量短硬设定“常驻注入”。其他条目优先通过本章显式关联命中，再用名称、别名、关键词辅助；所有选择可解释。关键词匹配适合稳定可预测的设定，语义检索将来可以作为辅助候选，但不能静默替代关键词结果。硬约束相互冲突时阻止生成并要求解决，不能仅按优先级掩盖。

世界书来源分层：全书世界书、作品阶段世界书、角色绑定条目、道具绑定条目、章节专属条目。它们合并后按照来源策略排序；同一事实只保留一个权威条目，其余卡片通过引用显示。重命名世界书或条目时保留稳定 ID，自动更新绑定关系并提示受影响章节。

世界书编辑器必须有“测试触发”功能：输入一段章节计划或正文片段，显示命中的条目、触发键、递归链、注入位置、排序、token 估算以及因预算未注入的条目。测试结果可保存到生成任务的 ContextSnapshot，保证作者看到的资料与模型收到的资料一致。世界书条目不会保证模型一定写出相关内容；它只改变上下文可用信息。

### 3.1.1 小说版条目模板

```text
条目：旧钟楼
主键：旧钟楼, 钟室, 北港钟楼
过滤：雾港 AND (夜航 OR 水闸)
触发：关键词 + 第 8 章地点关联
顺序：背景 30；章节约束 70
递归：允许 1 层，可触发“失踪船航海记录”
注入：本章资料区；作者秘密独立存放，按揭露限制裁剪
预算：约 180 tokens；硬设定
```

### 3.1.2 与角色卡、道具卡的边界

角色卡和道具卡是可维护的结构化实体，拥有动态状态、关系、持有人和正文证据；世界书条目是注入单元。一个角色可以绑定多条角色背景条目，一个道具也可以绑定使用规则条目，但卡片的当前状态不能只写在世界书正文里。生成前先读取按章状态，再决定是否激活绑定条目。

### 3.2 文风规则：把“去八股、去 AI 感”变成可编辑标准

文风不是一个保证有效的开关，也不提供“AI 含量”百分比。它由可执行规则、正反例、检查建议与作者选择组成。

规则字段：名称、分组、要求、正例、反例、强度（必须 / 尽量）、适用范围（全书 / 本章 / 选段）、启用状态、版本。

推荐分组：叙述视角、语言习惯、对话、节奏、描写、章节收尾。默认规则示例：

1. 采用第三人称限知，描述与推断受当前视角人物的信息边界约束。
2. 情绪优先通过行为、选择和对话体现；允许必要的心理描写，避免机械“一律禁止”。
3. 控制重复比喻、同构排比和固定过渡句，不把少数词语全面封禁。
4. 对话服务人物目的，角色措辞有差异，不让所有人充当设定讲解员。
5. 结尾由动作、问题或局势变化自然收束，不强制每章总结升华或制造悬念。
6. 润色默认保留剧情事实、信息揭露时机、人物立场与重要动作。

规则例：“避免抽象总结情绪。”反例：“一股复杂的情绪涌上心头。”正例：“他把写好的地址划掉，又问了一遍末班船的时间。”正例仅示范表达机制，不能每次照抄。

工作流程：生成前应用规则 → 生成后标出具体疑似问题及理由 → 作者选择局部修改 → 对改动重新检查事实。首版以确定性重复句式检查＋可选模型审稿为主，不承诺自动判断文学质量。

### 3.3 角色卡：固定档案与动态状态分离

- 固定档案：姓名、别名、身份、外观、核心欲望、恐惧、价值观、能力及限制、说话习惯。
- 动态状态：位置、身体与伤势、目标、关系变化、持有物、当前已知信息。
- 成长计划：预期转折、人物弧线；明确标为计划，不能当作已经发生。
- 信息边界：作者知道、角色知道、角色误信分别记录。
- 关系记录：角色 A → 角色 B 的认知与态度，必要时双向分别保存。
- 来源：每次状态变更绑定章节定稿版本、正文证据和确认记录。

例：作者知道凶手身份，但主角目前只知道船票是假票；正文不能因角色卡记录了真相就让主角直接报出凶手。

### 3.4 道具卡：跟踪归属、位置与能力边界

字段：名称、类型、外观、用途、使用条件、消耗与限制、秘密、首次出场、关联人物与世界引擎线索。

动态字段：当前持有人、存放位置、数量或耐久、损坏 / 封存 / 丢失等状态；保存获得、转移、使用、损毁的历史事件。

首版区分：唯一道具与可计数资源。唯一道具不允许两个当前持有人；数量型资源可记录数量变化。复杂库存堆叠、装备系统留后续。

例：第 7 章已确认交给配角的铜钥匙，第 8 章主角不能直接从口袋取出。系统给出冲突和来源，不擅自补写“又借了回来”。

### 3.5 大纲：把结构转成每章可执行的任务

层级：全书主线 → 卷目标 → 章节计划 → 可选场景。

章节计划包含：剧情目标、视角人物、地点与故事时间、入场状态、冲突、关键转折、结尾状态、出场角色、道具、要推进的世界引擎线索 / 事件、不可提前揭露的信息、目标字数。

状态：构思、已规划、写作中、已定稿。场景可记录目标与结果；不要把计划完成等同于正文已经发生。生成“下一章”前优先准备这份任务，而不是只有一个章名。

首版采用单主线章节顺序；闪回作为明确标注的场景时间处理，不自动把回忆场景状态覆盖到当前。多时间线自动推演留后续。

### 3.6 世界引擎：统一管理时间、行动与线索

世界引擎读取正文、世界书和角色 / 道具 / 技能状态，按章节、天、月或自定义天数推进故事时间，并保存角色行动、关系、事件、线索和工作笔记。它输出可审阅的推演提案，不直接把未确认的推测写回作品卡片。

线索可以记录表面信息、作者真相、关联实体、计划窗口和当前状态，但统一由世界引擎维护。只有作者确认提案后，状态变化才会成为下一次生成可使用的事实；正文尚未写出的计划不会被当成既成事实。

## 4. 贯穿六个模块的统一规则

### 4.0 世界书与提示词编排器

写作页右侧的“本次资料”只展示结果；独立的 `/books/:bookId/context` 用于编排发送给模型的上下文。它采用 SillyTavern Prompt Manager 的核心交互：可拖拽的提示块、启用 / 禁用、角色（system / user / assistant 的等价任务段）、相对顺序和任务触发范围。默认模板如下：

```text
系统约束 → 作品硬设定 → 文风规则 → 作者本章任务 → 角色 / 道具当前状态
→ 章节计划 → 世界书命中条目 → 前章摘要与近期正文 → 输出格式与收尾要求
```

提示块可以来自固定模板或世界书 outlet。一个 outlet 是命名资料槽，例如 `world_background`、`chapter_constraints`、`engine_hints`；条目只声明插入哪个槽，章节任务决定槽在上下文中的位置。这样可以保留灵活的提示词顺序，同时避免作者在每条资料里手工复制长提示。

上下文编排页面保存提示块清单和顺序；作品、本章可直接调整编排。不能用任意模板代码执行宏；变量使用白名单并在保存时校验。

与聊天软件不同，本项目不把章节历史当成无界聊天记录，也不把“消息深度”作为主要记忆机制。小说使用章序、场景时间和确认状态快照；必要时才把近期正文作为一个有版本号的资料块。

暂不照搬的机制：按消息深度扫描聊天记录、每次触发的随机概率、无来源的向量自动激活、依赖自由字符串宏的隐式逻辑。它们可以在后续实验模式加入，但生产生成必须能回答“为什么注入了这条资料”“为什么没有注入”“模型实际收到的顺序是什么”。

### 4.1 三种内容身份

每条事实或关系都要区分：作者设定、未来计划、已经在正文发生且确认的事实。AI 建议单独存储为待确认提案，不能直接覆盖前述任何类型。

稳定档案与按章变化的状态分开。查询“第 N 章开场状态”时取该章之前已确认的状态，不能把最新结局倒灌到前面的章节。首版使用状态事件＋按章快照即可，不引入完整事件溯源平台。

### 4.2 版本与引用

实体均有稳定 ID、作品 ID、创建 / 更新时间与修订号。生成记录固定当时资料版本和正文基线，不引用不断变化的“最新文本”。

来源至少保存章节版本 ID、短证据文本、可选编辑器锚点。正文修改导致锚点失效时标记需要复核，不默默把相邻文字当成证据。被引用的卡片优先归档而非直接删除。

### 4.3 改写旧章

旧章定稿修改后，该章提取摘要、状态变化与依赖它的后续上下文标记过期。给出受影响章节清单，允许逐章重新提取并确认；不自动改写后文，不继续使用失效状态而不提示。

## 5. 一次章节生成的完整闭环

1. 选择章节任务；检查模型能力、凭证、章计划和硬设定。
2. 先评估世界书：常驻条目、章节 / 卡片绑定、关键词命中、递归链和手动条目；按优先级合并，应用预算并记录裁剪原因。
3. 按提示词编排器组装本章资料：创作规则、文风、章计划、显式关联卡片、相关世界书、世界引擎状态、前文摘要和近期原文。按视角和故事进度裁剪信息。
4. 展示本次资料清单、触发依据、插入位置、缺失信息与输入量估算。硬性冲突先处理；一般缺失允许作者补充或明确继续。
5. 创建持久化任务，冻结输入版本；流式输出到候选草稿并周期保存。
6. 做基础检查；用户可发起模型审稿和选段润色。检查项显示原文片段、问题、依据、建议。
7. 作者采纳候选并定稿；如果生成期间正文已被编辑，先比较基线版本，不能直接覆盖。
8. 从定稿正文提取章节摘要、人物变化、道具变化和世界引擎事件，显示证据，生成待确认提案。
9. 作者接受 / 编辑 / 拒绝提案。后端校验后，在事务中写入状态变化与快照；下一章使用确认后的状态。

正文流、状态提取与审稿分开请求。正文与元数据混成一次大 JSON 会让流式展示和失败恢复更脆弱。

### 5.1 上下文预算

模型资料保存已知上下文窗口和输出上限；按提供方能力校验。预算需为输出、系统消息和估算误差留空间；中文按对应 tokenizer 计数或明确展示近似值，字数不等于 token 数。

优先保留：当前任务、短硬约束、视角边界、直接关联状态、本章关键线索；其次直接关键词命中、递归命中、近期原文与摘要、一般背景。裁剪采用“原文 → 已确认摘要 → 排除可选背景”的显式策略。必需内容仍放不下就提示调整，不能静默截断。常驻条目先计入预算，命中条目按照优先级和直接性排序；预算溢出必须显示告警。

首版使用手动关联＋别名关键词＋按章摘要；作品规模确实需要时再增加 SQLite FTS 或向量检索。无论检索方式如何，都提供来源、版本与命中原因。

## 6. API 管理与预设管理

### 6.1 API 预设

API 管理页面创建的是“API 预设”，不是泛化资料条目。每个预设是一组可复用的连接配置，字段：预设名称、协议枚举、提供方类型、自定义 Base URL、密钥引用、默认超时、并发上限、启用状态。默认协议为 `OpenAI Compatible`，后续可扩展 `Anthropic`、`Google Gemini` 和自定义 HTTP。

配置表单的模型字段是下拉选择。用户先选择协议并填写地址、密钥，然后点击“获取模型”；后端通过对应适配器拉取模型列表，返回模型 ID、能力和上下文上限，前端填入下拉栏。接口不支持模型列表时，允许手动添加模型并明确标记为手动模型。模型下拉选择结果保存到当前 API 配置，不重复保存地址和密钥。

支持连接测试、获取模型、手动添加模型与错误详情。连接测试和获取模型必须显示加载、成功、认证失败、限流、地址错误和协议不兼容状态，不能用“已连接”覆盖真实失败原因。

首版先完整支持 OpenAI 兼容接口；模型标识和地址由用户填写。后续按真实需求加入其他提供方原生适配器。不能把“兼容”当作所有参数、流式格式和模型列表均相同。

每个模型记录能力：流式、结构化输出、支持的参数、上下文与输出上限、价格及其录入日期。没有价格时费用显示未知；估算与提供方返回的实际 usage 分开显示，不编造用量。

密钥只在后端保存，本地使用加密存储，主密钥由操作系统凭据存储或环境变量提供，不与密文一起硬编码。页面只显示掩码，修改 / 替换时提交新值；响应、日志、导出不包含原密钥。默认导出不含凭证。

本地服务只绑定回环地址，校验访问来源；部署到局域网或公网时另加认证、权限、TLS 和自定义地址访问控制，不能直接沿用裸露的本地配置。

### 6.2 API 配置与上下文编排

- API 配置：连接、模型、协议和请求所需的凭证。
- 上下文编排：提示块来源、角色、位置、顺序、启用状态和 token 预算。
- 文风规则：语言、叙述、节奏及正反例，属于作品创作规则。

API 参数与提示块顺序分开保存，方便更换模型而不意外改变写作上下文。模板变量用固定白名单插值并在保存时校验，禁止把模板当可执行代码。

### 6.3 失败与取消

区分认证错误、限流、网络错误、不支持参数和提供方错误。自动重试仅用于安全重试的阶段并退避；已经输出正文后不自动从头重试或切换模型，以免重复计费和重复文本。

取消传播到上游请求；保留已生成草稿。界面明确说明取消不保证撤销提供方已发生的费用。首版异常任务可用新任务重试，不宣称所有厂商支持从精确断点续传。

## 7. 技术架构

采用 pnpm workspace 的模块化单体，保持可拆分但先不拆微服务。

| 层 | 首选 | 职责 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite | 页面与编辑器 |
| UI | Tailwind CSS + shadcn-vue | 统一组件、主题与布局 |
| 路由与 UI 状态 | Vue Router + Pinia | 当前作品、面板与临时交互 |
| 服务端数据 | TanStack Vue Query | 请求、缓存、失效刷新 |
| 正文 | Tiptap Vue 3 | 文档编辑、选段命令、内容序列化 |
| 后端 | Node.js 当前 LTS + Fastify + TypeScript | 服务端业务与 AI 请求 |
| 数据 | SQLite + Prisma | 持久化、迁移、事务 |
| 契约 | Zod + 共享 TypeScript 类型 | 请求及模型结构化输出校验 |
| 任务 | SQLite 任务表 + 单 worker | 长耗时生成、取消、恢复记录 |
| 输出流 | SSE | 增量正文与任务事件 |

版本在初始化时选择互相兼容的稳定版并锁定 lockfile。Pinia 不存全部后端实体作为第二份数据库；编辑器使用独立草稿状态和版本号保存。

```text
apps/
  web/src/
    app/                  路由、主题、全局布局
    features/
      library/ writer/ world/ characters/ items/
      outline/ world-engine/ style/ providers/
    components/           通用组件
    lib/                  HTTP、SSE、编辑器集成
  server/src/
    modules/              与业务模块对应的路由和服务
    ai/adapters/          提供方协议适配
    ai/context/           上下文选择与预算
    ai/context/           上下文编排与版本
    ai/checks/            规则与一致性检查
    jobs/                 调度、任务状态、事件
    storage/              数据、密钥与备份
packages/
  contracts/              Zod schemas 与接口类型
  db/                     Prisma schema 与迁移
docs/
  product-framework.md
```

生产本地版由 Fastify 提供前端静态文件与 API，尽量同源。开发版 Vite 代理 API。首版可以直接用提供方 SDK 或 HTTP 流适配，不必依赖大型 Agent 框架。

任务状态：queued → running → succeeded / failed / cancelled；进程退出遗留 running 任务在启动时标记 interrupted，保留部分输出供作者检查。任务事件带递增序号并持久化，页面重连可以重放事件，不等于重新请求模型。

基础接口示意：

```text
POST   /api/books
GET    /api/books/:bookId/chapters
PUT    /api/chapters/:id/draft          携带 baseRevision，冲突返回 409
POST   /api/chapters/:id/context-preview
POST   /api/generation-jobs            绑定上下文快照与正文基线
GET    /api/generation-jobs/:id/events  SSE，支持事件序号重连
POST   /api/generation-jobs/:id/cancel
POST   /api/chapters/:id/accept-version
POST   /api/change-proposals/:id/apply
POST   /api/providers/:id/test
```

后端校验作品归属、模型能力、输入版本和提案冲突；前端校验不能替代后端校验。同章默认只有一个正文生成任务，重复点击用幂等键避免重复创建。

## 8. 最小数据模型

| 实体 | 内容 |
| --- | --- |
| Book / Volume / Chapter | 作品元信息、排序、章状态 |
| ChapterVersion | 不可变正文版本、Tiptap JSON、纯文本、来源、父版本 |
| WorldBook / WorldEntry / WorldEntryBinding | 世界书、触发条目、作品 / 角色 / 道具 / 章节绑定 |
| WorldActivation / ContextOutlet / PromptBlock | 本次命中记录、命名资料槽、可排序提示块 |
| StyleProfile / StyleRule | 世界条目与写作约束 |
| Character / CharacterRelation / Item | 稳定档案、定向关系与道具 |
| OutlineNode / ChapterEntityLink | 层级计划、本章显式引用 |
| WorldEngineState / WorldEngineEvent | 世界时间、后台行动、线索与已确认事件 |
| EntityStateChange / ChapterStateSnapshot | 动态变化与按章状态 |
| ChapterSummary / ChangeProposal | 来源版本、摘要、待确认提案与证据 |
| ProviderConnection / Model | API 连接和模型配置 |
| ContextSnapshot / ContextItem / GenerationJob / GenerationEvent | 固化触发结果、上下文顺序、任务及增量事件 |

查询与约束常用字段建独立列和索引；可变扩展字段用经过校验的 JSON。不要把整个小说放在一个大 JSON 字段，也不必一开始做任意类型的通用卡片引擎。关联字段使用外键，并限制跨作品引用。

提案应用使用事务和预期修订号。例如道具转移必须核对旧持有人；同一提案不能重复应用。版本恢复创建新版本，不删除历史。正文自动保存做防抖＋显式状态提示，失败保留本地草稿恢复副本，不能显示虚假的“已保存”。

导出首版支持正文 TXT / Markdown，以及不含密钥的结构化项目备份。数据库使用 SQLite 支持的备份方式，避免运行中只复制主文件而漏掉 WAL。恢复先校验格式与版本，在新位置验证后再替换。

## 9. 分阶段实施与验收

### A. 本地创作骨架

作品书架、布局、章节编辑、自动保存、版本历史、六类资料的基础增删改查和关联、项目备份。

验收：创建两部作品后数据互不串联；刷新与重启不丢内容；恢复旧版本不损坏历史；未配置 API 时仍可手工写作。

### B. 真实 AI 写作闭环

连接与预设管理、模型能力校验、世界书触发与预算、提示块编排、章计划、上下文预览、流式生成、取消、候选比较与采纳。

验收：用真实配置生成一章；能看到每条资料的触发键、来源、注入位置和裁剪原因；修改关键词测试文本会改变命中预览；取消保留部分草稿；网络错误可恢复界面；刷新不会触发重复模型请求；编辑期间生成不能覆盖新文字。

### C. 连续性与文风

摘要、状态提案、确认入库、道具归属检查、角色知情边界、世界引擎证据与时间窗口、文风规则检查和局部改写。

验收案例：铜钥匙转交后下一章不能无依据回到主角手中；角色不会把未来计划视作既有经历；“计划埋设”未写进正文不能变成“已埋设”；旧章改写能提示后续资料过期；润色保留既有事实。

完成 A–C 才是具备基本长篇能力的首版。优先以 5–10 章样本验证稳定性，再增加批量任务、关系图、时间线可视化、向量检索、原生多厂商协议、桌面打包和云同步。
